# Chapter 14: Data Access: EF Core and Dapper

## 1. Learning Objectives
By the end of this chapter, you will be able to:
- Understand the internal mechanics of the Entity Framework (EF) Core Change Tracker.
- Optimize EF Core queries using `AsNoTracking`, Projections, and Query Translation analysis.
- Utilize Dapper for bare-metal, high-performance read queries.
- Architect Connection Pooling and Resiliency strategies for cloud databases.

## 2. Introduction

Data is the lifeblood of an enterprise application. C# objects in RAM are ephemeral; they disappear when the server reboots or crashes. To persist data, we must serialize it and send it to a relational database (like SQL Server or PostgreSQL).

In the .NET ecosystem, two paradigms dominate Data Access:
1. **Object-Relational Mapping (ORM) via EF Core:** Highly productive, stateful, automatically translates C# LINQ to SQL, and manages relationship graphs.
2. **Micro-ORM via Dapper:** Explicit, stateless, bare-metal SQL mapping. Trades development speed for absolute execution speed.

A Senior C# Architect does not choose between them; they use both. In a CQRS architecture (Chapter 12), we use EF Core for complex **Commands** (Writes) and Dapper for lightning-fast **Queries** (Reads).

## 3. Entity Framework Core: Internals and The Change Tracker

EF Core is a massive architectural achievement. It allows you to query a database using C# LINQ, and it translates that LINQ into optimized SQL at runtime.

### The DbContext and Change Tracker
When you fetch an entity using EF Core, it is tracked by the `DbContext`.

```csharp
// 1. Fetch from DB
var charger = await _dbContext.Chargers.FindAsync("CHG-1");

// 2. Modify object in memory (C#)
charger.Status = ChargerStatus.Faulted;

// 3. Save Changes
await _dbContext.SaveChangesAsync();
```

**What happens internally?**
1. During the query, EF Core materializes the SQL result into a `Charger` object.
2. It takes a "snapshot" of the original values and stores them in the **Change Tracker** (a dictionary held inside the `DbContext` instance).
3. When you change `charger.Status`, only the C# object changes.
4. When you call `SaveChangesAsync()`, EF Core iterates through the Change Tracker. It compares the current object state against the original snapshot.
5. It detects that *only* the `Status` property changed. It generates a highly specific SQL statement: `UPDATE Chargers SET Status = 2 WHERE Id = 'CHG-1';`

**Performance Warning:** 
The Change Tracker consumes significant memory and CPU. If you query 10,000 records to generate a report, storing 10,000 snapshots in the Change Tracker will cause massive GC pressure and application slowdowns.

### `AsNoTracking()`
If you are reading data strictly to display it (and have no intention of calling `SaveChanges`), you MUST disable the Change Tracker.

```csharp
var activeChargers = await _dbContext.Chargers
    .AsNoTracking() // Bypasses the Change Tracker completely
    .Where(c => c.IsOnline)
    .ToListAsync();
```

## 4. Query Translation and N+1 Problems

When you write a LINQ query, EF Core parses the Expression Tree generated by the Roslyn compiler and translates it into SQL. 

```csharp
// C# LINQ
var heavyChargers = await _dbContext.Chargers
    .Where(c => c.MaxKw > 100)
    .ToListAsync();
```
*Translates to:* `SELECT [c].[Id], [c].[MaxKw] FROM [Chargers] AS [c] WHERE [c].[MaxKw] > 100`

### The N+1 Problem (Lazy Loading)
If you have a relationship (e.g., a `Tenant` has many `Chargers`), fetching them incorrectly causes the **N+1 Query Problem**, the most common performance killer in ORMs.

```csharp
// 1 Query to get 100 Tenants
var tenants = await _dbContext.Tenants.ToListAsync(); 

foreach (var t in tenants)
{
    // If Lazy Loading is enabled, this triggers ONE QUERY PER TENANT!
    // Total Queries: 1 (for tenants) + 100 (for chargers) = 101 Queries!
    Console.WriteLine(t.Chargers.Count); 
}
```

**The Fix:** Eager Loading via `.Include()` or Projection via `.Select()`.

```csharp
// Projection: Translates into a single, highly optimized SQL JOIN
var tenantData = await _dbContext.Tenants
    .Select(t => new {
        t.Name,
        ChargerCount = t.Chargers.Count
    })
    .ToListAsync();
```

## 5. Dapper: Bare-Metal Performance

While EF Core is excellent for tracking state changes, it generates a lot of overhead. If you are building a dashboard query that joins 5 tables and aggregates millions of rows, EF Core's SQL generation might be sub-optimal, and object materialization is slow.

**Dapper** (built by Stack Overflow) is an extension method over `IDbConnection`. It does not track state. It does not translate LINQ. You write raw SQL, and Dapper uses Reflection (via heavily cached IL generation/DynamicMethods) to map the result set to C# objects instantaneously.

```csharp
using Dapper;
using Microsoft.Data.SqlClient;

public class DashboardQuery
{
    private readonly string _connectionString;

    public async Task<List<ChargerStatsDto>> GetStatsAsync(Guid tenantId)
    {
        using var connection = new SqlConnection(_connectionString);
        
        string sql = @"
            SELECT 
                c.Id, 
                c.MaxKw, 
                SUM(s.KwDelivered) as TotalEnergy
            FROM Chargers c
            LEFT JOIN Sessions s ON c.Id = s.ChargerId
            WHERE c.TenantId = @TenantId
            GROUP BY c.Id, c.MaxKw";

        // Dapper maps the raw SQL to the C# record instantly.
        var result = await connection.QueryAsync<ChargerStatsDto>(sql, new { TenantId = tenantId });
        
        return result.AsList();
    }
}

public record ChargerStatsDto(string Id, decimal MaxKw, decimal TotalEnergy);
```

## 6. Connection Pooling

Opening a physical TCP connection to a database is extremely slow (often taking tens of milliseconds).

ADO.NET provides **Connection Pooling**. When you dispose an `SqlConnection` (e.g., via the `using` statement), the underlying physical connection is *not* closed. It is returned to a hidden pool in RAM. The next time you create an `SqlConnection` with the exact same connection string, ADO.NET hands you an already-open connection from the pool instantly.

**Architectural Warning:** If you "leak" connections by forgetting to call `Dispose()`, the pool will empty out. The next time you request a connection, the application will block indefinitely and crash with a Timeout Exception. Always use `using`.

## 7. Real Production Case Study: Repository Implementation

In Chapter 12, we defined `IChargerRepository`. Let's implement it using EF Core for write operations.

```csharp
public class SqlChargerRepository : IChargerRepository
{
    private readonly EvDbContext _db;

    public SqlChargerRepository(EvDbContext db)
    {
        // DbContext is injected as a Scoped service
        _db = db;
    }

    public async Task<Charger> GetByIdAsync(string id)
    {
        // Tracking is enabled by default. We want tracking because
        // the Application Layer will modify this object.
        var charger = await _db.Chargers.FindAsync(id);
        
        if (charger == null) throw new NotFoundException(id);
        return charger;
    }

    public async Task SaveAsync(Charger charger)
    {
        // Because of the Change Tracker, EF Core already knows if 'charger' 
        // was modified. We just call SaveChangesAsync.
        await _db.SaveChangesAsync();
    }
}
```

## 8. Common Mistakes

| Level | Mistake | Impact | How to Avoid |
|-------|---------|--------|--------------|
| Beginner | Not using `AsNoTracking()` for read-only queries. | High memory usage, slow queries, GC pressure. | Add `.AsNoTracking()` to any LINQ query where you do not intend to call `SaveChanges`. |
| Intermediate | Evaluating LINQ on the client side. | Downloading millions of rows into RAM. | Pay attention to IDE warnings. If you use a C# method inside a `.Where()` that EF cannot translate to SQL, it will fetch the entire table to RAM and filter it locally. |
| Senior | Relying on EF Core for Bulk Updates. | Doing `foreach(var item in list) { item.Status = 1; } SaveChanges()` generates 10,000 separate `UPDATE` SQL statements. | Use `ExecuteUpdateAsync()` (EF Core 7+) or Dapper to execute a single `UPDATE ... WHERE IN (...)` statement. |
| Architect | Ignoring SQL Indexes. | Table scans lock the DB. | Use EF Migrations or DBA scripts to ensure Foreign Keys and frequently queried columns are indexed. |

## 9. Summary
Data Access is where enterprise applications live or die by performance. By understanding the EF Core Change Tracker, we can utilize it for safe, transactional Domain mutations while avoiding its memory penalties on read operations using `AsNoTracking()` and Projections. For absolute bare-metal speed on complex reporting queries, we drop down to Dapper.

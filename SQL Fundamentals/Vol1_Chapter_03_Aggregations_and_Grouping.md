# Volume 1, Chapter 3 – Aggregations and Grouping

## 1. Concept Overview

A relational database is designed to store millions (or billions) of rows. While retrieving individual rows is necessary for a web application to display a user's profile, business intelligence and analytics require summarizing massive datasets into digestible metrics.

This is achieved using **Aggregate Functions**. These functions perform a calculation on a set of values (a column) and return a single scalar value. For example, instead of returning 10,000 individual ticket prices, an aggregate function returns the "Total Revenue" (a single number).

## 2. The 5 Core Aggregate Functions

Every major relational database engine supports the ANSI standard Big Five aggregate functions.

### `COUNT()`
Counts the number of rows.
```sql
-- 1. Count all rows in a table (Includes NULLs)
SELECT COUNT(*) FROM Users;

-- 2. Count specific column (Ignores NULLs in that column)
SELECT COUNT(PhoneNumber) FROM Users;

-- 3. Count unique values (How many distinct cities have hosted events?)
SELECT COUNT(DISTINCT City) FROM Events;
```

### `SUM()`
Calculates the total sum of a numeric column.
```sql
-- Total revenue generated by all tickets
SELECT SUM(Price) FROM Tickets;
```

### `AVG()`
Calculates the mathematical average of a numeric column.
```sql
-- Average ticket price across the platform
SELECT AVG(Price) FROM Tickets;
```

### `MAX()` & `MIN()`
Finds the highest and lowest values in a column. This works on numbers, dates, and even text (alphabetically).
```sql
-- Find the most expensive ticket and the cheapest ticket
SELECT MAX(Price) AS HighestPrice, MIN(Price) AS LowestPrice FROM Tickets;

-- Find the date of the very first event we ever hosted
SELECT MIN(Date) FROM Events;
```

## 3. Grouping Data (`GROUP BY`)

Using an aggregate function on its own gives you the grand total for the *entire* table. But what if the CEO asks: "What is the total revenue **per event**?"

To answer this, we must use the `GROUP BY` clause. This instructs the database to split the data into "buckets" based on a specific column (e.g., EventID), and then run the aggregate function independently *inside each bucket*.

```sql
-- Calculate Total Revenue for EACH Event
SELECT 
    EventID, 
    SUM(Price) AS TotalRevenue
FROM Tickets
GROUP BY EventID;

-- Count how many users live in each city
SELECT 
    City, 
    COUNT(UserID) AS UserCount
FROM Users
GROUP BY City;
```

**The Golden Rule of `GROUP BY`:** 
If you use an aggregate function (`SUM`, `COUNT`) alongside a normal column (`EventID`, `City`) in your `SELECT` statement, **every normal column MUST be included in the `GROUP BY` clause.** If you forget it, the database will throw a syntax error.

```sql
-- ERROR: Column 'Events.Title' is invalid in the select list because it is not contained in either an aggregate function or the GROUP BY clause.
SELECT EventID, Title, SUM(Capacity) FROM Events GROUP BY EventID;

-- CORRECT FIX:
SELECT EventID, Title, SUM(Capacity) FROM Events GROUP BY EventID, Title;
```

## 4. Filtering Aggregates (`HAVING` vs `WHERE`)

The most common mistake junior developers make is confusing `WHERE` and `HAVING`.

*   **`WHERE`** filters rows *before* they are grouped and aggregated.
*   **`HAVING`** filters the result set *after* the groups and aggregations are calculated.

**Scenario:** The CEO wants to see the total revenue per event, but *only* for events that made more than $100,000.

```sql
-- THIS WILL FAIL (Syntax Error)
-- You cannot use an aggregate function inside a WHERE clause.
SELECT EventID, SUM(Price) 
FROM Tickets 
WHERE SUM(Price) > 100000 
GROUP BY EventID;

-- CORRECT APPROACH (Using HAVING)
SELECT EventID, SUM(Price) AS TotalRevenue
FROM Tickets 
GROUP BY EventID
HAVING SUM(Price) > 100000;
```

**Combining `WHERE` and `HAVING`:**
You can (and often should) use both in the same query.
"Show me the total revenue per event, but only for events in New York, and only show events that made more than $100,000."
```sql
SELECT EventID, SUM(Price) AS TotalRevenue
FROM Tickets 
WHERE City = 'New York'     -- 1. Filter rows FIRST (Fast!)
GROUP BY EventID            -- 2. Group the remaining rows
HAVING SUM(Price) > 100000; -- 3. Filter the aggregated totals LAST
```

## 5. SQL Server vs PostgreSQL Nuances

### `COUNT(1)` vs `COUNT(*)`
Historically, developers argued that `COUNT(1)` was faster than `COUNT(*)` because the database didn't have to look up the column definitions. 
**Truth:** In both modern SQL Server and PostgreSQL, the Query Optimizer rewrites `COUNT(1)` to `COUNT(*)`. They are physically identical in execution. `COUNT(*)` is the ANSI standard and preferred for readability.

### Handling `NULL` in Averages
Both SQL Server and Postgres ignore `NULL` values when calculating `AVG()`. 
If you have 3 tickets: `$100`, `$200`, and `NULL`.
*   The database calculates `(100 + 200) / 2 = 150`.
*   If you wanted the `NULL` to be treated as `$0`, you must use `COALESCE`: `AVG(COALESCE(Price, 0))`. This changes the math to `(100 + 200 + 0) / 3 = 100`.

## 7. Interview Questions

**Entry Level**
*   **Q:** What is the difference between `COUNT(*)` and `COUNT(ColumnName)`?
    *   **A:** `COUNT(*)` counts every row in the table (or group) regardless of the data inside it. `COUNT(ColumnName)` counts every row where that specific column is *not null*.
*   **Q:** Why does SQL throw an error if you don't put a non-aggregated column in the `GROUP BY` clause?
    *   **A:** Because it is mathematically impossible to render. If you ask for `SUM(Price)` and `City`, but you don't group by `City`, the database has 1 total sum, but 50 different cities. It doesn't know which city to print next to the grand total.

**Intermediate Level**
*   **Q:** Explain the exact difference between `WHERE` and `HAVING`.
    *   **A:** `WHERE` applies to individual rows *before* grouping occurs. `HAVING` applies to the calculated aggregates *after* grouping occurs. You should always push filters into the `WHERE` clause if possible to reduce the dataset size before the CPU-intensive `GROUP BY` operation occurs.

# Volume 1, Chapter 5 – Constraints and Keys

## 1. Concept Overview

A relational database is not just a digital filing cabinet; it is a strict gatekeeper. If you allow developers to insert any data they want, your database will quickly become a swamp of corrupted, orphaned, and duplicated data (e.g., tickets tied to users who don't exist, or negative ticket prices).

We enforce **Data Integrity** using **Keys** and **Constraints**. These are rigid, mathematical rules applied at the table level. If an `INSERT` or `UPDATE` statement violates a rule, the database engine violently rejects the transaction and throws an error.

## 2. The Primary Key (PK)

The Primary Key is the most important constraint in a relational database. It guarantees that **every row in a table is uniquely identifiable**. 
A Primary Key column cannot contain duplicate values, and it absolutely cannot contain `NULL` values.

*   **Surrogate Key:** A meaningless, auto-incrementing integer (1, 2, 3...) or a random UUID generated by the database. This is the industry standard for 99% of modern tables.
*   **Natural Key:** A key that has real-world meaning, like a Social Security Number or an Email Address. (Architects generally avoid these because real-world data changes—people change their emails—which breaks database relationships).

```sql
-- Creating a table with a Surrogate Primary Key
CREATE TABLE Users (
    -- SQL Server syntax for auto-incrementing surrogate key
    UserID INT IDENTITY(1,1) PRIMARY KEY,
    Email VARCHAR(100)
);
```

## 3. The Foreign Key (FK)

A Foreign Key creates a physical link between two tables, enforcing **Referential Integrity**.
If the `Tickets` table has a `UserID` column, that column is a Foreign Key pointing back to the Primary Key of the `Users` table. 

Because of this constraint, you **cannot** insert a ticket for `UserID = 99` if User 99 does not exist in the Users table. Furthermore, you **cannot** delete User 99 if they still own tickets, unless you explicitly configure a **Cascading Delete**.

```sql
CREATE TABLE Tickets (
    TicketID INT IDENTITY(1,1) PRIMARY KEY,
    UserID INT NOT NULL,
    EventID INT NOT NULL,
    Price DECIMAL(10,2),
    
    -- Enforcing the Foreign Key Relationship
    CONSTRAINT FK_Tickets_Users FOREIGN KEY (UserID) REFERENCES Users(UserID),
    
    -- Example of Cascading Delete (If Event is deleted, delete all its tickets automatically)
    CONSTRAINT FK_Tickets_Events FOREIGN KEY (EventID) REFERENCES Events(EventID) ON DELETE CASCADE
);
```

## 4. Academic Key Terminology

You will often hear these terms in university courses or interviews:

*   **Super Key:** Any combination of columns that uniquely identifies a row. (e.g., `UserID` + `Email` + `FirstName` together form a Super Key).
*   **Candidate Key:** The minimal Super Key. The smallest combination of columns that uniquely identifies a row. A table might have multiple Candidate Keys (e.g., `UserID` and `SSN`).
*   **Primary Key:** The single Candidate Key that the database architect *chooses* to act as the official identifier for the table.
*   **Alternate Key:** Any Candidate Key that was *not* chosen to be the Primary Key. (e.g., If `UserID` is the PK, `SSN` is an Alternate Key).
*   **Composite Key:** A Primary Key made up of two or more columns combined. Often used in many-to-many mapping tables (e.g., `EventID` + `TagID` in an `EventTags` table).

## 5. Additional Data Constraints

Besides Keys, SQL provides four major constraints to ensure business logic validity.

### `UNIQUE` Constraint
Ensures all values in a column are distinct. Unlike a Primary Key, a table can have multiple UNIQUE constraints, and a UNIQUE column *can* accept a `NULL` value.
```sql
-- No two users can have the same email
ALTER TABLE Users ADD CONSTRAINT UQ_Email UNIQUE (Email);
```

### `NOT NULL` Constraint
Forces a column to always contain a value.
```sql
-- A ticket must always have a price
ALTER TABLE Tickets ALTER COLUMN Price DECIMAL(10,2) NOT NULL;
```

### `CHECK` Constraint
Enforces a specific boolean condition. This is how you prevent negative prices or invalid statuses from entering the database.
```sql
-- Prevent negative ticket prices
ALTER TABLE Tickets ADD CONSTRAINT CHK_PositivePrice CHECK (Price >= 0);

-- Restrict Status to specific text values
ALTER TABLE Tickets ADD CONSTRAINT CHK_ValidStatus CHECK (Status IN ('Available', 'Sold', 'Reserved'));
```

### `DEFAULT` Constraint
If a developer forgets to provide a value during an `INSERT`, the database will automatically insert the default value.
```sql
-- Automatically log the current time when a user registers
ALTER TABLE Users ADD CONSTRAINT DEF_CreatedAt DEFAULT GETDATE() FOR CreatedAt;
```

## 7. Interview Questions

**Entry Level**
*   **Q:** What is the difference between a Primary Key and a Unique Constraint?
    *   **A:** A table can only have one Primary Key, and it cannot contain NULLs. A table can have multiple Unique Constraints, and they generally allow one NULL value.
*   **Q:** What does a Foreign Key do?
    *   **A:** It enforces referential integrity. It guarantees that the value in the child table must exist in the parent table. It prevents "orphaned" records.

**Intermediate Level**
*   **Q:** What is a Candidate Key?
    *   **A:** A Candidate Key is a minimal set of columns that can uniquely identify a row. A DBA looks at all the Candidate Keys in a table and selects one of them to serve as the official Primary Key.
*   **Q:** What happens if you try to delete a row in the `Users` table that has matching rows in the `Tickets` table?
    *   **A:** By default, the database will throw a Foreign Key constraint violation error and block the deletion. To allow it, the Foreign Key must have been explicitly created with the `ON DELETE CASCADE` rule, which would automatically delete the child tickets.
